# brief-01 (Settings screen) — 4-way ablation

## Brief

[`brief-01-settings-screen.md`](../../brief-01-settings-screen.md): "Build a SwiftUI Settings screen with three toggles (Notifications, Dark Mode, Sound) and a destructive Logout button at the bottom. Target iOS 26+." The brief exercises `color-and-contrast`, `spatial-design`, `sf-symbols`, `interaction-design`, `typography`, and `ux-writing` reference docs — enough surface area to expose differences between conditions.

## Conditions

All four `.swift` files parse and typecheck cleanly against the iOS 26 SDK (`xcrun swiftc -typecheck -sdk iphoneos -target arm64-apple-ios26.0`).

### C1 — No skill (vanilla baseline)

Plain `VStack` layout, hand-rolled rows, `Color.red` fill on the Logout button, hex-valued off-white background via `Color(red:green:blue:)`, fixed `.font(.system(size: 16))` on every label, no `#Preview` variants beyond the default, no accessibility affordances. No `Form`, no `List`, no SF Symbols, no `role: .destructive`. The "AI SwiftUI tutorial screenshot" archetype described in `impeccable/SKILL.md`'s reflex list.

### C2 — impeccable (web, cross-ported)

Applies web impeccable's craft instincts — visible type hierarchy, semantic tokens (albeit as private hex-derived `Color` constants), card shadow, a subtitle beneath the title, pixel-unit spacing (`20`, `24`, `32` rather than strict 4pt rhythm). Still hand-rolls the grouped list instead of using `Form`. Destructive button is visually thoughtful (tinted background + border) but uses a custom `Color(red:green:blue:)` rather than `role: .destructive`. No SF Symbols, no `Label`, no `@ScaledMetric`, no `#Preview` variants.

### C3 — impeccable-swift (the fork)

`NavigationStack` + `Form` + `.formStyle(.grouped)`. Every row is `Toggle(isOn:) { Label("…", systemImage: "…") }`. Logout uses `Button(role: .destructive)` with `rectangle.portrait.and.arrow.right` via `Label`, plus `.accessibilityLabel` and `.accessibilityHint`. Wraps the tap in a `.confirmationDialog` for a safer destructive action. Uses `@ScaledMetric` relative to `.body` / `.title3`. Ships three `#Preview` variants: Light, Dark, and Dynamic Type `accessibility2`. Matches what the reference docs describe.

### C4 — Sean's Claude setup (no impeccable skill)

Follows `DESIGN-SWIFT.md.template` explicitly — semantic `AppColor` enum, `AppSpacing` scale on the 4pt grid, 8pt corner radius, two-level shadow, 44pt `minHeight` on tappable rows, `.buttonStyle(.borderedProminent)` with `.tint(AppColor.destructive)`, sentence-case copy ("Log out", "Dark mode"). Visibly more tasteful than C1 or C2 — but does not reach for `Form`, `Label` + SF Symbol, `@ScaledMetric`, or `#Preview` variants. The template doesn't mandate those; impeccable-swift does.

## Concrete observations (not a ranking)

1. **`Form` adoption is the sharpest dividing line.** Only C3 uses `Form { Section { Toggle … } }`. C1, C2, and C4 all hand-roll a `VStack` of rows with manual dividers and padding. C4 produces a cleaner hand-roll than C1 or C2, but it's still a hand-roll — tap targets, safe-area insets, and list affordances are reimplemented by hand instead of inherited from the platform.
2. **`@ScaledMetric` and `#Preview` variants only appear in C3.** C4 uses Dynamic Type-compatible patterns (semantic `Color`, 44pt heights, spacing scale) but does not reach for `@ScaledMetric` or preview the view under Dynamic Type / dark mode. Those are specific impeccable-swift conventions, not general refined-minimal ones.
3. **SF Symbols only appear in C3.** C1 has no icons at all. C2 omits them entirely — web-impeccable instincts don't reach for SF Symbol as the default icon channel. C4 omits them because the `DESIGN-SWIFT.md.template` does not mandate them; Sean's preset leaves icon decisions to the project.
4. **`role: .destructive` vs hand-colored red.** C1 uses `Color.red` directly; C2 uses a custom RGB destructive tint with an opacity wash; C4 uses `.tint(AppColor.destructive)` on `.borderedProminent`; only C3 uses `Button(role: .destructive)` — the HIG-blessed way to express destructive intent, which the system then renders in the appropriate dark-mode-aware destructive red and routes correctly through accessibility.
5. **Copy casing and plainness improved as skills were added.** C1 says "Logout" and "Dark Mode". C2 and C4 say "Log out" / "Dark mode" (sentence case, Apple voice). C3 adds a confirmation dialog with plain language ("You can sign back in anytime."). The brief's `ux-writing` signal is visible in all three skilled conditions.

## Limitations (the simulation caveat)

- **Single-session role-play, not four isolated environments.** A subagent inherits one environment; I cannot truly swap skill configurations mid-run. Each condition was generated by constraining my own behavior to match what that configuration would produce, informed by actually reading the reference docs, the `DESIGN-SWIFT.md.template`, and the critique/impeccable SKILL.md files. This is honest directional evidence, not clean-room ablation data.
- **No rendered UI screenshots.** The grid image shows the _code produced_ per condition rather than rendered SwiftUI views. Rendering each view would have required an iOS simulator boot per condition, with small incremental signal for this POC — the code-level differences are already clear. Rendering is left as future work (a Playground or ChatBenchmark-style harness would do it).
- **Author bias.** I wrote both the skill and the eval. C3 will naturally reflect what I had in mind when I wrote the reference docs. The observations section is written to avoid "C3 wins" framing, but the author-as-evaluator risk is real.

## What would make this more rigorous next time

- **Four separate Claude sessions, four machines or four fresh profiles.** True environment isolation, not role-play.
- **Automated detector counts per file.** Run `swiftlint` + `impeccable-lint` + the asset-catalog-checker against each `.swift` file and publish the violation-count delta. The infrastructure for this already exists in `tools/`.
- **Blind designer review.** Hand the four files to a third party with quadrant labels stripped. Ask them to rank on 6 dimensions (structure, type, color, interaction, a11y, copy) and record where the rankings cluster vs. diverge.
- **More briefs across the grid.** Run all three `brief-*.md` files through all four conditions. A single brief cannot generalize.
- **Rendered screenshots, not code cards.** Build a tiny `ChatBenchmark`-style SwiftUI harness that hosts each view and exports a `.png` per condition. That makes the grid scan as four UIs rather than four blocks of code, which is what a casual reader of the tweet/README will want.
